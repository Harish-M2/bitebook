## 1. Project Overview

**Bitebook** is a premium, dark-mode, image-first social food diary and discovery app
(React Native + Expo). It is inspired by the social-discovery/diary concept of
Letterboxd, applied to food — but Bitebook is an original product: no Letterboxd
branding, assets, UI, or code has been copied.

Core product loop:

```
DISCOVER → TRY → LOG → RATE → SHARE → FOLLOW → DISCOVER AGAIN
```

Users discover dishes/restaurants, log what they've eaten (diary), rate and review
dishes, share with followers, and follow other users to discover more. The master
product/UX/engineering spec is `docs/Bitebook_Build_Instructions.md`; the master visual
reference is `docs/Bitebook_UI_Concept.png`. **These two files remain the source of truth
for product/design decisions and must not be modified without explicit user instruction.**

Current product direction: MVP-first, backend-second. Phase 1 built the full dark UI
shell with mock data; Phase 2 built the real Supabase backend (schema, RLS, auth,
storage) without touching the Phase 1 UI. Phase 3 (not started) will wire real data into
the UI and integrate a restaurant data provider.

## 4. Application Architecture

- **Startup**: `src/app/_layout.tsx` is the Expo Router root layout. It loads Inter fonts,
  wraps the app in `GestureHandlerRootView` → `SafeAreaProvider` → `AuthProvider`, forces
  `StatusBar style="light"` (app is dark-only per spec), and renders a `Stack` with no
  header, background colour from `colors.background`.
- **Navigation**: Expo Router, file-based. A `(tabs)` group holds the 5 main screens
  (home, discover, log, diary, profile). Root `index.tsx` exists — its redirect logic
  should be checked/confirmed (**NEEDS VERIFICATION**: read `src/app/index.tsx` to confirm
  whether it currently redirects to `/home` unconditionally or has any auth-gating logic).
- **Authentication**: `AuthProvider` (`src/hooks/useAuth.tsx`) wraps the whole app; see §5.
- **State management**: no global state library (Redux/Zustand/etc.) — React context
  (`AuthProvider`) plus local component state. Data-fetching is done via small functions in
  `src/lib/db/*.ts` calling the shared `supabase` client directly (no React Query/SWR
  currently wired in — **NEEDS VERIFICATION** if this remains true on the Mac; check
  `package.json` for any data-fetching library before assuming otherwise).
- **Database access**: `src/lib/supabase.ts` exports a single typed `supabase` client
  (`createClient<Database>(...)`). Table-specific helper functions live under
  `src/lib/db/` (currently only `profiles.ts`). Convention: keep route files thin, put
  data/business logic in `src/lib/db/*.ts`, keep UI presentational in `src/components/`.
- **Components**: `src/components/ui/` holds reusable design-system primitives (Button,
  Chip, Rating, Screen, Surface, Typography, Skeleton, EmptyState, ErrorState, Avatar,
  IconButton, SearchBar). `src/components/food/` holds food-domain components (DishCard,
  FoodDiaryItem, RestaurantRow). Reuse these — do not create parallel/duplicate
  components for the same concept.
- **Mock data**: `src/mock-data/*.ts` still backs most/all screens as of this handover.
  Real Supabase wiring beyond auth/profile has **not** been done — this is intentional
  (Phase 2's explicit scope was backend-only, no UI/mock-data replacement). See §17.
- **Supabase client**: gracefully degrades if env vars are missing (logs a warning,
  falls back to a placeholder URL/key so the app doesn't crash on boot) — see §5/§9.

## 6. Database Architecture

This section summarizes `docs/database-architecture.md`, which is the authoritative,
more detailed description — read that file directly for full detail. It documents what
the migrations **actually create**, not aspirational design.

**22 application tables**, created across 23 migration files (`supabase/migrations/0001`
through `0023`):

`profiles`, `restaurants`, `restaurant_sources`, `restaurant_photos`, `cuisines`,
`restaurant_cuisines`, `dishes`, `dish_photos`, `dish_cuisines`, `reviews`,
`review_photos`, `diary_entries`, `saved_dishes`, `follows`, `likes`, `comments`,
`lists`, `list_items`, `notifications`, `taste_preferences`,
`user_cuisine_preferences`, `reports`.

Key structural points (see `docs/database-architecture.md` for full detail):

- **`profiles`**: 1:1 with `auth.users`, `username` nullable + case-insensitive unique
  (`citext` + partial unique index), created only by trigger.
- **`restaurants`**: `location geography(Point,4326)` is the sole authoritative location
  value; `latitude`/`longitude` are ordinary stored columns kept in sync by a
  `BEFORE INSERT OR UPDATE` trigger (`sync_restaurant_lat_lng()`) — **not** generated
  columns (this was deliberately changed during the Phase 2 correction pass; see §14/§15).
  Restaurants are **not client-writable** — no INSERT/UPDATE/DELETE RLS policy exists.
- **`dishes`**: scoped to a restaurant, `normalized_name` generated column +
  unique constraint prevents case/whitespace duplicate dish names per restaurant. Clients
  *can* INSERT dishes (unlike restaurants).
- **`reviews`**: has `visibility` enum (`public` / `followers` / `private`); a shared
  `can_view_review(owner_id, visibility)` SQL function gates read access, reused by
  `review_photos`, `likes`, and `comments` so they inherit the parent review's visibility.
- **`diary_entries`**: always private to the owner; `review_id` is backed by a
  **composite foreign key** `(review_id, review_user_id, review_dish_id) →
  reviews(id, user_id, dish_id)` with shadow columns auto-synced by a trigger, guaranteeing
  a diary entry can only link to a review by the same user about the same dish; `UNIQUE
  (review_id)` also guarantees one diary entry per review.
- **`saved_dishes`**: partial unique indexes on `(user_id, dish_id)` and
  `(user_id, restaurant_id)` (each `WHERE ... IS NOT NULL`) make "want to eat" and "saved"
  mutually exclusive per item.
- **Denormalised counters** (trigger-maintained, never client-writable): `reviews.
  like_count`/`comment_count`, `dishes.aggregate_rating`/`rating_count`,
  `profiles.dishes_logged_count`/`restaurants_visited_count`/`average_rating`/
  `cuisines_explored_count`.
- **PostGIS**: `restaurants_location_gix` GiST index; `public.nearby_restaurants(lat,
  lng, radius_meters, max_results)` RPC (`SECURITY INVOKER`, parameterised, never raw
  client SQL) in `0022_rpc.sql`.
- **Cuisine taxonomy**: seeded via `0023_seed_cuisines.sql` (real migration, not
  `seed.sql`, since it's reference data needed in every environment).
- **Storage buckets**: `avatars`, `dish-photos`, `restaurant-photos` (all public-read),
  `review-photos` (private — visibility-gated SELECT policy). See §7.

**Do not invent new tables/fields.** If a UI feature needs a column that doesn't exist,
stop and flag it — do not silently add speculative schema.

## 7. RLS / Security

Full detail in `docs/database-architecture.md` §3/§4/§12 — summary:

- **RLS is enabled on every one of the 22 tables** (`0019_rls.sql`). No table relies
  solely on application-layer checks.
- **profiles**: public read; owner-only update; no client insert/delete.
- **restaurants**: public read; **zero client write policies** (no INSERT/UPDATE/DELETE) —
  this was a deliberate fix (see §14) after a static audit found a client-INSERT policy
  that contradicted the approved architecture.
- **dishes**: public read; authenticated users may INSERT (attributed via
  `created_by_profile_id`).
- **restaurant_sources / restaurant_photos / cuisines / *_cuisines**: public read only, no
  client INSERT at all — reserved for a future server-side provider-sync function.
- **reviews**: visibility-gated read (`public`/`followers`/`private` via
  `can_view_review()`); owner-only insert/update/delete.
- **review_photos / likes / comments**: inherit the parent review's visibility via
  `can_view_review()` — a private/followers-only review's photos/likes/comments are
  invisible to unauthorized users even though these child tables have no `visibility`
  column of their own.
- **diary_entries**: strictly owner-only, no visibility concept at all.
- **saved_dishes / lists / list_items / user_cuisine_preferences**: owner-managed;
  `lists` additionally supports `is_public` for third-party read access.
- **follows**: public-read graph edges; only the follower can create/delete their own
  edge; self-follow blocked by a CHECK constraint.
- **notifications / taste_preferences**: system-generated only, no client INSERT.
- **reports**: client can INSERT their own report; **no SELECT/UPDATE/DELETE policy at
  all** — moderation data, accessible only via the service-role key (server-side only,
  never in client code).
- **Storage security**: `avatars`/`dish-photos`/`restaurant-photos` are public-read;
  `review-photos` is a **private bucket** whose SELECT policy performs a live join back to
  `reviews.visibility`/`follows` using the same `can_view_review()` function as table RLS.
- **SECURITY DEFINER functions** (`handle_new_user`, all counter trigger functions,
  `can_view_review`) all have `set search_path = public` pinned. `nearby_restaurants()` is
  intentionally `SECURITY INVOKER` (relies on the caller's own RLS-gated SELECT
  permissions on `restaurants`, since restaurants are public-read anyway). The new
  `sync_restaurant_lat_lng()` trigger function does not use SECURITY DEFINER (it only
  operates on the row being written, no elevated privilege needed).

**Still needs verification (see §13):** all of the above has been reviewed via static SQL
reading and two rounds of self-audit, but **no RLS policy has actually been exercised
against a running database yet** — see §13 for exactly what remains unverified at
runtime.

## 15. Important Product Decisions

Do not accidentally reverse these:

- Bitebook is **dark-mode only** for the MVP — no light theme toggle (`app.json`
  `userInterfaceStyle: "dark"`, forced `StatusBar style="light"`, `tailwind.config.js`
  `darkMode: 'class'`).
- **No paid restaurant API** is integrated in Phase 2 (explicit, repeated user
  instruction). Restaurant records in Phase 2 use only `manual` / `user_submitted` /
  `seed` sources. The multi-provider architecture (`restaurant_sources`) exists
  structurally so a real provider can be added later without a schema change — do not
  remove or simplify this table structure.
- **Restaurants are not client-writable.** This was a deliberate security fix — do not
  re-add a client INSERT/UPDATE/DELETE policy on `restaurants` without a documented
  architectural decision to do so.
- **PostGIS `location` is the single authoritative geographic value**; `latitude`/
  `longitude` are trigger-derived convenience columns, never independently writable in
  practice. Do not reintroduce three independently-writable location values.
- **Review visibility model**: `public` / `followers` / `private`, inherited by
  `review_photos`/`likes`/`comments` via `can_view_review()`. Do not add a separate
  visibility concept to the child tables — inheritance via the parent review is the
  approved design.
- **Diary entries are always private** — no visibility concept, unlike reviews.
- **Email/password auth only** for MVP — no Google/Apple sign-in yet (explicit scope
  decision, not an oversight).
- **No fake/placeholder usernames** are ever generated — `username` stays `NULL` until
  the user completes onboarding; `display_name` (not `username`) is what's populated at
  signup.
- **Service-role key is never used in client code** — only the anon/publishable key.
- Bitebook is explicitly **not** a Letterboxd clone — original branding/UI/copy only.

## 21. Troubleshooting

**npm install issues**
- If install fails on peer-dependency conflicts, check the Expo SDK version compatibility
  table for SDK 57 — do not force-downgrade `react`/`react-native` versions, as they are
  pinned to match Expo 57's requirements exactly.
- Delete `node_modules` and `package-lock.json`-derived cache (`rm -rf node_modules`,
  `npm cache clean --force`) and reinstall if you hit unexplained resolution errors.

**Expo issues**
- Run `npx expo-doctor` first for any "app won't start" issue — it checks for common
  config/dependency mismatches.
- If Metro bundler hangs or shows stale code, clear cache: `npx expo start --clear`.
- Since the app is dark-only, if you see light-mode rendering unexpectedly, check
  `tailwind.config.js` `darkMode: 'class'` is intact and NativeWind's Babel plugin is
  still configured in `babel.config.js`.

**Supabase CLI issues**
- `npx supabase login` opens a browser flow — ensure you're logged into the correct
  Supabase account that has access to the "Bitebook" project (organization
  `rtudzhljlcsgezxorbfd`).
- `npx supabase link --project-ref discsdmiuatiwtldmcoc` — if this fails with a
  permissions error, you (or the account you're using) may not yet have been added as a
  collaborator on the Supabase project; request access before proceeding.
- `supabase migration list --linked` failing to connect usually means either not logged
  in, or not linked yet — re-run `login` then `link`.

**Docker issues**
- `supabase test db` / `supabase start` failing with a Docker error means Docker Desktop
  is either not installed or not running. On Mac: install from
  https://docs.docker.com/desktop/setup/install/mac-install/, then ensure the Docker
  Desktop app is actually launched/running (not just installed) before retrying.

**Environment variable issues**
- If the app boots but every Supabase call fails/network-errors, check the console for
  the `[Bitebook] Missing Supabase environment variables` warning — this means `.env` is
  missing or the two `EXPO_PUBLIC_*` keys are empty. Expo requires a full restart
  (`npx expo start --clear`) after editing `.env`; hot reload does not pick up new env
  vars.

**Authentication issues**
- Since there's no sign-in UI yet, testing auth currently requires calling
  `signInWithPassword`/`signUpWithPassword` from `useAuth()` manually (e.g. via a
  temporary debug button) or using the Supabase dashboard's Auth panel to create a test
  user directly.
- If a signed-up user has no matching `profiles` row, check that the
  `handle_new_user()` trigger is actually present on the linked database (it should be,
  per `0002_profiles.sql` and the confirmed migration list) — this would indicate the
  migrations were not actually fully applied despite `migration list` reporting so;
  investigate via the Supabase dashboard's Database → Functions/Triggers view.

**Database migration issues**
- Never hand-edit the remote schema via the Supabase dashboard's SQL editor for anything
  that should be permanent — always add a new migration file instead, so the repository
  remains the single source of truth and `migration list --linked` stays in sync.
- If `migration list --linked` shows a mismatch (a migration present remotely but not
  locally, or vice versa), stop and investigate before pushing/resetting anything — do
  not force-reset the remote database without understanding why they diverged.

**TypeScript issues**
- If regenerating `src/types/database.ts` from `--linked` introduces type errors
  elsewhere in the app, fix them incrementally rather than reverting to the
  hand-authored file — the generated file is the more trustworthy long-term source.

**Git issues**
- Standard `git pull`/`push` should work with no special LFS/submodule setup — this repo
  has neither, as confirmed by the absence of `.gitattributes`/`.gitmodules` in the file
  listing.
